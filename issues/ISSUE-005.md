# ISSUE-005: "最低价"含税不含税混着排，那个 ◀ 箭头我不敢信

- 提交人: User A | 日期: 2026-10-24 | 状态: 重复关闭（Duplicate of ISSUE-001，随其回归）
- 类型: 💡体验

## 问题描述（我在做什么时遇到了什么，用户视角）

我按 README 抄命令查大阪（`search --from SHA --to KIX`），结果排第一的"最低价" ¥1009 标着"**不含税**"，第二名的抖音团购券 ¥1099 是"**含税**"。我最后付给航司的钱永远是含税总价，所以这两个数根本没法直接比：¥1009 加上税之后，说不定比 ¥1099 还贵。工具说"最低价一眼可见"，但这里我盯着屏幕看了半天也看不出到底哪个便宜——那个 ◀ 箭头指的价，可能根本不是我到手要付的价。

## 复现步骤

1. 运行 `python src/fareradar.py search --from SHA --to KIX --date 2026-12-20`。
2. 观察结果第 1 行（模拟航司源，不含税）与第 2 行（抖音团购源，含税）的"含税/不含税"标注与"◀ 最低价"标记。
3. （可由总协调者补充：确认排序是否按展示价格直接比较、是否考虑了税费口径统一。）

## 预期结果

所有价格按同一种用户真实支付的口径（含税总价）排序比较；如果某票源只有不含税价，就别让它参与"最低价"标记，或者明示"¥1009 + 税费，到手价未知/约 ¥X"。

## 实际结果

不含税的 ¥1009 被标为"◀ 最低价"，含税的 ¥1099 排在它后面；用户无法判断真实总价高低，"最低价"标记可能误导决策。

       ◀ 最低价

## 对用户的影响

对预算敏感的人来说，"先报低价、付款时加税"是最常见也最烦的套路。工具本来看穿这个套路，结果自己的"最低价"标记也犯了同样的毛病。我不敢按箭头做决定，等于最核心的功能对我失效。
