# ISSUE-018: 空结果三态未区分——`200 + 0 条` 与 `204 无数据` 混为一谈

- 提交人: 总协调者（v1.10.1 交付后对真实缓存做覆盖统计时发现） | 日期: 2026-10-25 | 状态: Closed（v1.10.2）
- 类型: 🐛Bug（提示不精确）
- 严重程度: **P2**（不影响数据真实性，也不误导为"有数据"，但让用户无法判断该不该换航线）
- 前序: ISSUE-017（v1.10.1 已区分 204，但只区分了这一种）

## 发现过程

v1.10.1 交付后核对 `.rapidapi_cache/` 里 12 条真实查询记录，发现空结果有两种上游语义：

| 航线/日期 | 上游 body status | 行程数 | 实测含义 |
|---|---|---|---|
| INC→CTU 2026-10-28/10-31/11-01/11-03 | **204** | 0 | 上游无此航线数据（`No content`） |
| INC→CAN 2026-11-01 | **200** | 0 | 查询成功，但未返回可售行程 |
| INC→PEK 2026-11-01 | **200** | 0 | 同上 |
| INC→WUH 2026-11-01 | **200** | 0 | 同上 |
| INC→SHA / INC→SZX 2026-11-01 | 200 | 4 / 6 | 正常 |

关键证据：INC→CAN（银川→广州）**有 v1.5 的航旅纵横实测快照证明该航线真实存在航班**，但上游返回
200 + 0 条。说明这不是"航线不存在"，而是"上游这次没给出可售报价"。

## 实际结果 / 期望结果

- 实际：`200 + 0 条` 走 `empty_note()` 返回 `None`，界面回落到笼统的"该航线暂无可用报价"。
- 期望：明确区分「上游没有这条航线的数据」（204）与「查询成功但没有可售行程」（200 + 0 条），
  后者不应让用户误以为航线不存在。

## 修复

1. `rapidapi_sky.empty_note()` 增加 `status == 200` 分支：
   "上游查询成功但未返回可售行程（可能有航班但无可售报价，或该日期尚无排班）"。
2. 旧缓存（v1.10.0 及更早，无 `body_status` 字段）仍返回 `None`——不猜原因。
3. **沉淀为通用约定**：`docs/03-tech-design.md` 新增第 9 节「网络票源适配器通用约定」，
   把 status 校验、空/非空缓存 TTL 分级、空结果原因可区分、原因只读缓存、不编造五条写死，
   作为后续新增联网适配器的强制要求（ISSUE-017 遗留建议一并关闭）。

## 验证

- 单测 **176 例全绿**（+1：200+0 与 204 文案必须不同）。
- 四种情形实机核对：

| 情形 | 文案 |
|---|---|
| INC→CAN 2026-11-01（200+0） | 上游查询成功但未返回可售行程（可能有航班但无可售报价，或该日期尚无排班） |
| INC→CTU 2026-11-01（204） | 上游 Google Flights 无该航线数据（status 204：No content） |
| SHA→CAN 2026-11-05（旧格式缓存） | `None`（回落兜底文案，不猜） |
| INC→SZX 2026-11-01（有报价） | `None`（有报价就不该有原因说明） |

- 本次未消耗真实配额（全部为缓存读取与离线单测）。

## 遗留

1. 上游对国内航线的覆盖是产品级限制，本单仍只解决"说清楚"。评估付费档或快照补充见 HANDOFF §4 第 4 条。
2. `INC→CAN` 这类"有真实航班但上游无报价"的航线，是最适合补实测快照的对象（零配额消耗）。
