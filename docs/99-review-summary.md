## 一、项目成果一句话

以真实软件公司研发流程（参照 project.md），由总协调者带领 PM/研发/测试/用户四个子代理，完整交付了 **低价票雷达 FareRadar v1.0.0 → v1.1.0**：一个纯标准库 Python 命令行比价工具（航司直连 + 抖音团购票源），并完整走通了 6 个 Issue 从提交到关闭的研发闭环。

## 二、产品在用户眼中是怎样的（本项目主线）

- **它是什么**：用户打开 README，3 分钟内能做三件事——比价（`search`）、看团购券有没有坑（`deals`）、设底价盯降价（`watch`）。
- **它怎么对用户诚实**：所有含价格的输出首行声明"模拟数据，不能用于实际购票"；团购卡必含价格/航线/有效期/退改规则/"需在抖音 App 内下单"；缺字段显示"未披露"并给行动指引。
- **用户说它好不好**：v1.0 用户评价——"像懂行的朋友帮我画重点……但它偶尔把过期传单塞给我"；v1.1 用户评价——"箭头终于只指我真能买到的便宜，我更愿意用了"。这前后两句用户原话，就是本项目从 v1.0.0 到 v1.1.0 的全部意义。
- **用户的吐槽直接驱动了产品**：6 个 Issue 中 3 个来自用户旅程的真实卡点，其中"售罄券标最低价"（ISSUE-004）是用户最痛、最先修复的一个。

## 四、流程证据：8 环节闭环怎么走的

`Issue Submitted → Triage → Reproduce → Fix → Code Review → Test → User Acceptance → Closed`

- **Issue Submitted**：Tester（001~003，正式黑盒测试）与 User A（004~006，真实旅程卡点）各自按模板提交，含复现步骤/预期/实际/证据/用户影响。
- **Triage**：PM 逐单定性定级并公开答复；裁定 3 个口径问题（到手价=含税价优先、有效期=可出行窗口、禁止补数据消灭"未披露"场景）；005 判重复关闭互链。
- **Reproduce**：Dev 在每个 issue 内留痕复现结果与根因（定位到具体函数与原因）。
- **Fix**：每个 Issue 独立分支 fix/issue-00X（叠放管理），修复+新增 14 例回归测试。
- **Code Review**：总协调者逐支审阅 diff、复跑全量单测、实测场景；PR-001~006 全部有书面评审记录；v1.0 的"先合并后评审"流程问题被评审指出并在 v1.1 全程纠正。
- **Test**：Tester 回归 5/5 单原问题不再复现，20 条既有用例（5 条按 PRD v1.1 改写）通过，35 例单测全绿，无新回归。
- **User Acceptance**：User A 逐卡点重验通过，"原有好用的地方没坏"；QA 报告的 002/003 以 QA 回归代替用户验收并在 Closed 节说明理由与重开路径。
- **Closed**：PM 关闭全部 6 单并关联 PR/合并提交/版本；用户新观察 2 项列入 backlog。

## 六、抖音团购（春秋航空等）低价票源接入探索结论

- **现状**：航司在抖音直播/团购渠道发放超低价套餐券，对价格敏感用户价值真实，但限制条件（有效期/预约/退改/行李额）是最大信息不对称。
- **接入路径**：只走官方路径（抖音开放平台/本地生活服务商资质 + 与航司商务合作）；第三方聚合需法务评审；**未经授权爬取不采用**（违反平台协议、账号与法律风险）。
- **本期落地**：MVP 用模拟源 + 统一 `Source` 适配器契约（deal_id/航线/含税口径/有效期/库存/购买入口/退改规则），真实接入时只需新增一个适配器实现并在注册表登记，产品层零改动——这是"探索"在架构上的答案。
- **产品层已内置对团购票风险的用户保护**：退改不明标记、售罄不推荐、有效期不覆盖不推荐、"需在抖音 App 内下单"提示。

## 七、各角色做了什么（对应 project.md 面试问题）

- **PM**：模糊需求收敛成 3 命令小而完整的 V1.0；用户反馈驱动 PRD v1.1；分诊中 3 次关键口径裁定；拒绝为凑数量虚报问题。→"你如何分析模糊需求并确定核心功能？""用户反馈多时如何定优先级？"
- **研发**：可插拔适配器架构让"探索抖音接入"变成零风险增量；5 个修复根因定位到函数级；从"先合并后评审"被纠正到主动配合流程。→"你如何使用 Git 协作？""AI 生成的代码如何保证可靠？"
- **测试**：20 条用例按 PRD 验收标准设计，3 条失败全部转化为高价值 Issue；回归时按新语义改写用例而非机械重跑。→"你如何设计测试用例？""如何判断是缺陷还是需求问题？"
- **用户**：以非工程师视角走真实旅程，贡献了团队最痛的发现（ISSUE-004）；验收时同时检查"有没有把好用的弄坏"。→"产品在用户眼中是怎样的？"的最佳注脚。
- **总协调者**：派工与交接中转、冒烟验证、6 份 PR 评审、流程纪律（评审先于合并）、全程留痕。
