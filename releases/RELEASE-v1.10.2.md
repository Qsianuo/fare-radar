## 这版解决了什么（一句话）

空结果现在分得清三种情况：**这条航线上游没有数据** / **查到了但没可售报价** / **真的没航班**——
不再一律说"暂无可用报价"。

## 修复

- **【ISSUE-018】`200 + 0 条` 与 `204` 混为一谈**：v1.10.1 只区分了 204。实测发现上游还有
  `200` + 0 条行程的情况（查询成功，但没有可售报价）。最典型的反例是 银川→广州：v1.5 的
  航旅纵横实测快照证明这条航线真实有航班，上游却返回 200 + 0 条——如果按"无此航线"解释就错了。

| 情形 | v1.10.1 | v1.10.2 |
|---|---|---|
| 204 | 上游 Google Flights 无该航线数据 | 同（不变） |
| 200 + 0 条 | 该航线暂无可用报价（笼统） | 上游查询成功但未返回可售行程（可能有航班但无可售报价，或该日期尚无排班） |
| 旧缓存（无 status） | 笼统 | 同（不猜原因） |

## 沉淀：网络票源适配器通用约定

`docs/03-tech-design.md` 新增第 9 节，把这几轮踩出来的经验写成**后续新增联网适配器的强制约定**：

1. 必须校验响应体 `status`，不能只看 HTTP 状态码
2. 空结果与正常结果的缓存 TTL 必须分开（空结果 30 分钟）
3. 空结果必须给出可区分的原因，不得只显示"暂无可用报价"
4. 原因说明只读缓存，不得回源（不额外烧配额）
5. 不编造补充：字段缺失即 `None`，未知枚举不猜中文，脏数据丢弃

## 质量

- **176 例全绿**（+1 例：`200+0` 与 `204` 文案必须不同）
- 四种情形实机核对通过：`200+0` / `204` / 旧格式缓存（返回 `None`）/ 有报价（返回 `None`）
- 本次**未消耗任何真实配额**（全部为缓存读取与离线单测）

## 已知限制

1. `200+0` 的具体原因（无报价 / 无排班）上游不细分，本项目只能在文案里如实列为可能性。
2. 可查到的航线数量不变——上游覆盖是产品级限制。
3. 最适合补实测快照的正是 `INC→CAN` 这类"有真实航班但上游无报价"的航线（零配额消耗）。
