## 这版解决了什么（一句话）

以前产品只能告诉你「最低 ¥630」，现在还会告诉你 **630 是正常价、偏便宜还是偏贵**——
依据是上游 Google Flights 的行情统计（本次最低 / 常规区间 / 近 60 天趋势）。

## 新增能力

### 行情参考（Web 仪表区 / MCP / CLI 三入口同源）

- **Web**：搜索后仪表区出现「行情参考」块——等级标签（偏低 / 正常价 / 偏高）、本次最低价、
  常规区间、近 60 天价格范围，附口径说明。无数据时整块不出现。
- **MCP**：`search_flights` 输出在航线行之后增加一行行情：
  `行情参考（RapidAPI·Google Flights 口径）｜正常价｜本次最低 ¥630｜常规区间 ¥440–680｜近 61 天 ¥430–640（抽样）`
- **CLI**：`search` 输出同样一行，位置在"临近日期最低价"之后。

### 数据纪律（这一版的重点不是功能，是这几条）

| 规则 | 落地方式 |
|---|---|
| 零额外配额 | 行情只读已有的 6 小时结果缓存，**永不回源**（有单测锁定） |
| 零编造 | 字段缺失 → 整块隐藏；脏历史点丢弃；未知等级不猜中文 |
| 口径不混用 | 行情与 `_to_offer` 的含税总价同口径，不换算、不叠加机建燃油 |
| 三入口同源 | 取数与文案只写在 `fareradar.py` 一处，Web/CLI/MCP 共用 |

## 顺带修掉一个真实的工程隐患

`tests/test_v14_features.py` 从 v1.5 起就漏了离线注入三行，却调用 `all_sources()` 9 次——
**每次跑全量测试都会真实联网消耗配额**。本次实测证据：跑一次测试，计数从 17/11 涨到 20/14（+3）。
补齐后复测，计数器 20 → 20 不变。这是 HANDOFF §6 第 1 条同一坑的第三次复发。

## 认知更正（如实记录）

实施前把 `lowest_price` 理解为"历史最低"，实测证明它是**本次查询最低价**（630 = 当日最便宜
行程 ¥630），历史最低在 `price_history`（430）。判断贵/便宜要依据 `price_level` 与
`typical_price_range`，不是 `lowest_price`。

## 质量

- **170 例全绿（1.3s 全离线）**，新增 5 例。
- 端到端：CLI / MCP / Web `/api/search` 三入口均输出行情，内联 JS 通过 `node --check`。
- 端到端验证复用已付费的响应落缓存复现，未额外消耗配额。

## 已知限制

1. `price_history` 是上游**抽样价位**（61 天仅 6 个不同价位），只能当趋势参考，不要当逐日行情。
2. 行情随缓存生命周期更新（6 小时）；缓存缺失时整块隐藏，不显示过期数据。
3. 目前仅 RapidAPI·Google Flights 渠道提供行情，其他渠道无此能力属正常缺省。
4. 月配额天花板未变（自设 90 次 / 上游 100 次），行情本身不占配额。
